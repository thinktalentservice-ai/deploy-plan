1 The architecture

One domain. The Worker is the only thing you "operate" — everything else is fully managed and idles to zero.

yourdomain.com (Cloudflare DNS — one zone) │ ┌──────────────────────────────────┐ │ CLOUDFLARE WORKER (front door) │ ← WAF · DDoS · TLS · routing └──────────────────────────────────┘ │ ├─ app1.yourdomain.com ─┐ ├─ app2.yourdomain.com ─┤→ Cloudflare Workers + OpenNext │ … ×100 Next.js apps │ (SSR/ISR/RSC · scale-to-zero · same cloud) │ ┘ │ ├─ yourdomain.com/api/* ──→ Google Cloud Run ×200 │ ├ FastAPI (native scale-to-zero) │ └ Spring (GraalVM native image) │ │ │ Neon Postgres (serverless, idles to zero) │ └─ yourdomain.com/api/* ──→ Azure Container Apps (alt backend) 180k vCPU-sec + 360k GiB-sec + 2M req/mo FREE always
No load balancer, no NAT, no VPC to run. The Worker does host/path routing at the edge. Frontends are on Cloudflare itself — adding the Worker route is enough, no proxy hop. Backends get a stable *.run.app URL each; the Worker forwards /api/* to them. Azure Container Apps backends get a stable *.azurecontainerapps.io URL.

Verdict for this low-budget build: Cloudflare Worker. It has a $0 floor (GCP LB bills ~$18/mo before any traffic), bundles WAF + DDoS for free, and gives real routing logic for the 300-project KV map. The only thing you give up is native Cloud Run integration — the cross-cloud hop adds a few ms and pennies of egress, which is negligible at low budget. The same Worker can route to Azure Container Apps backends with no extra setup. Go GCP Global LB only if you decide to keep frontends on Cloud Run too and want everything inside one cloud.
Hybrid option: you can use both — Cloudflare Worker as the public front door (cheap edge + WAF + DDoS), proxying to a GCP internal LB that fans out to Cloud Run via serverless NEGs. Best security (origins never public) but one more component to run; skip it unless you need locked-down origins.

4 The single-domain router Worker

KV-driven so adding/moving any of the 300 projects is a data write — no redeploy. Subdomains for Next.js apps, /api/* paths for backends (Cloud Run or Azure Container Apps).

worker.js
// Route map lives in KV (binding: ROUTES). Example values:
//   host:app1   -> https://app1.pages.dev              (Next.js on CF)
//   path:/api/users -> https://api-users-xxx.run.app    (Cloud Run)
//   path:/api/orders -> https://orders.agreeablehill.azurecontainerapps.io  (Azure Container Apps)

export default {
  async fetch(request, env, ctx) {
    const url = new URL(request.url);
    const sub = url.hostname.split(".")[0];

    // 1) subdomain -> Next.js app
    let target = await env.ROUTES.get(`host:${sub}`);

    // 2) path -> backend API (Cloud Run or Azure Container Apps)
    if (!target && url.pathname.startsWith("/api/")) {
      const svc = url.pathname.split("/")[2];        // /api/users -> users
      target = await env.ROUTES.get(`path:${svc}`);
    }
    if (!target) return new Response("No route", { status: 404 });

    // forward, preserving path + query
    const originUrl = new URL(url.pathname + url.search, target);
    const req = new Request(originUrl, request);
    req.headers.set("X-Forwarded-Host", url.hostname);
    req.headers.set("X-Origin-Secret", env.ORIGIN_SECRET);  // lock origins

    // edge-cache GETs to cut backend wakeups + cost
    if (request.method === "GET") {
      const cache = caches.default;
      let res = await cache.match(req);
      if (res) return res;
      res = await fetch(req);
      if (res.ok) ctx.waitUntil(cache.put(req, res.clone()));
      return res;
    }
    return fetch(req);
  },
};
Lock your origins: the Worker sends X-Origin-Secret; set Cloud Run ingress to reject anything without it (or use internal ingress + the secret). For Azure Container Apps, use a custom ingress rule or Azure API Management (dev tier) to validate the header. That stops anyone bypassing your domain/WAF by hitting the *.run.app or *.azurecontainerapps.io URL directly.

5 Deploy quickstart

A Next.js app → Cloudflare

  1. Add adapter: npm i @opennextjs/cloudflare
  2. Build: npx opennextjs-cloudflare build
  3. Deploy: npx wrangler deploy
  4. Map subdomain app1.yourdomain.com in CF DNS → done

A FastAPI / Spring API → Cloud Run

  1. Containerize (FastAPI: simple Dockerfile; Spring: GraalVM native image)
  2. Deploy: gcloud run deploy api-users --source . --min-instances=0
  3. Cap cost: add --max-instances=5 --cpu=1 --memory=512Mi
  4. Register the *.run.app URL in the Worker's KV map

A FastAPI / Node API → Azure Container Apps

  1. Containerize: standard Dockerfile, push to Azure Container Registry (free 10 GB)
  2. Create environment: az containerapp env create --name myEnv --resource-group myRG --location eastus
  3. Deploy: az containerapp create --name api-orders --resource-group myRG --environment myEnv --image myacr.azurecr.io/api-orders:latest --min-replicas 0 --max-replicas 5 --ingress external --target-port 8000
  4. Register the *.azurecontainerapps.io URL in the CF Worker's KV map

A static frontend → Azure Static Web Apps

  1. Connect GitHub repo in Azure portal → Static Web Apps → create
  2. GitHub Actions workflow auto-generated — push to deploy
  3. Custom domain: map app1.yourdomain.com CNAME to the SWA URL
  4. Register the subdomain in CF Worker KV map (or point CF DNS directly)
Spring Boot note: plain JVM cold-starts 10–30s → 502s on wake. Compile a GraalVM native image (cold start ~0.3–0.7s) and set Hikari minimum-idle=0 so an idle DB pool doesn't keep the container awake. FastAPI works out of the box (cold start ~1–3s). Azure Container Apps and Cloud Run behave identically for this pattern.
