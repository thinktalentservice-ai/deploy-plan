  • Free best-in-class WAF/DDoS at the edge; one place to secure 300 apps

Enterprise governance, single cloud → GCP. Heavy/regulated with a platform team → AWS. Microsoft-ecosystem / hybrid/on-prem integration → Azure.

1 Architecture per option

How the 300 projects (100 frontend + 200 backend) are wired in each.

AWS

Route 53 (DNS, one domain) │ CloudFront (CDN + WAF + TLS, edge cache) │ ALB (path/host routing, 300 target groups) │ ECS Fargate tasks ×300 ├ 100 frontend containers (Next.js/static) └ 200 backend containers (FastAPI / Spring) │ NAT GW + VPC + RDS/Aurora + ECR

Most moving parts. Each backend = a Fargate service behind an ALB rule. Frontends can sit in S3+CloudFront instead of Fargate to cut cost.

Vercel + Railway + Cloudflare

Cloudflare Worker (one domain, router) │ ├─> Vercel 100 frontend projects │ (edge CDN + SSR, built in) │ └─> Railway 200 backend services ├ FastAPI (sleep ✓ native) └ Spring (GraalVM native img) serverless = sleep after 10min

No load balancer to manage — Worker does host/path routing. Each platform handles its own TLS, CDN, autoscale. Least infra.

GCP

Cloud DNS (one domain) │ Global External LB + Cloud CDN + Cloud Armor (WAF) │ Cloud Run services ×300 ├ 100 frontend (container/static) └ 200 backend (FastAPI / Spring) │ scale-to-zero, per-100ms billing │ Cloud SQL + Artifact Registry

Cloud Run gives each service an HTTPS URL for free; the Global LB unifies them under one domain + adds CDN/WAF. Serverless without leaving one cloud.

Key structural difference

AWS = you assemble + run the load balancer, NAT, VPC, scaling rules. Power + tax.

Stack = three managed PaaS, the Worker is the only thing you "operate".

GCP = one cloud, serverless containers, managed LB/CDN. Middle ground: serverless economics + hyperscaler governance.

Scale-to-zero? AWS Fargate: not natively (needs scheduled scaling / EventBridge). Railway: yes (sleep). Cloud Run: yes (native, the default).

★ Variant ④ — GCP Serverless + Cloudflare (hybrid of ② & ③)

Cloudflare Worker (one domain, router + WAF + cache) │ free DDoS / WAF / TLS / edge cache │ origin-lock secret header │ ├─> Cloud Run 100 frontend (Next.js/OpenNext) │ └─> Cloud Run 200 backend (FastAPI / Spring) ingress = internal + LB only scale-to-zero, per-100ms │ Cloud SQL / Neon + Artifact Registry

Same Cloud Run economics as option ③, but the Worker replaces the ~$18/mo Global LB. The Worker terminates TLS, applies WAF/DDoS for free, edge-caches GETs (cutting GCP egress and backend wake-ups), and routes host/path to each service's internal URL.

Origin locking is mandatory: set Cloud Run ingress to internal + Cloud Load Balancing or require an X-Origin-Secret the Worker injects, so attackers can't hit the *.run.app URL directly and skip the edge.

AWS deep-dive: ECS on EC2 (t3a.2xlarge) — On-Demand vs Spot

Instead of Fargate (per-task premium), run the ECS cluster on raw EC2 and bin-pack all 300 containers onto a few big instances. t3a.2xlarge = 8 vCPU / 32 GB / AMD, on-demand $0.3008/hr ($219.58/mo), spot ~$0.112/hr (~63% off).

Capacity math (bin-packing 300 containers)

300 services × ~256 MB avg = ~77 GB RAM needed. Usable RAM/instance ≈ 30 GB (after ECS agent + OS). 77 ÷ 30 ≈ 3 instances; add HA across 2 AZs + headroom → 4 × t3a.2xlarge (32 vCPU / 128 GB total). Tune up/down with real RAM per service.

The catch with EC2 on-demand: you pay for whole instances 24/7 — no scale-to-zero. With 300 mostly-idle services, on-demand EC2 ($1,030) is actually worse than Fargate ($650), which at least bills per running task. EC2 only wins when you keep utilization high (>70% bin-packing) and/or use Spot.
Spot is the real lever (~63% off). All-Spot lands at ~$477/mo — cheaper than Fargate and the closest AWS gets to the PaaS-stack price. Trade-off: Spot instances can be reclaimed with a 2-min warning, so run a capacity-provider strategy = small On-Demand baseline (keeps the fleet alive) + Spot for the bulk, with ECS auto-replacing drained instances. The Mixed row (~$753) is the production-safe middle: HA guaranteed, ~14% cheaper than pure on-demand.
EC2 vs Fargate, when: EC2 + Spot + dense bin-packing → best AWS unit economics at scale (this fleet). Fargate → less ops, better for spiky/unpredictable per-task load and true pay-per-task. For 300 long-lived services, EC2 Spot with a mixed capacity provider is the cost-optimal AWS choice — but it's the most ops to run (cluster scaling, AMI patching, draining, Spot interruption handling).

Regulated workloads (HIPAA/PCI/FedRAMP): AWS or GCP — both sign BAAs and carry the full cert stack. The PaaS stack is fine for standard SaaS but Railway's compliance posture is lighter; Cloudflare's edge security is the strongest single piece in any of the three.
Misconfig risk: AWS gives the most rope — public S3 buckets, open security groups, over-broad IAM are the classic breaches. More knobs = more ways to get it wrong. The PaaS stack has fewer knobs, so fewer self-inflicted holes, but you also can't lock things down as tightly.

4.1  Defense-in-depth — who owns each layer

Same request path (edge → network → app → data), graded per stack. More green = more security handled for you.

AWS

  • Edge: CloudFront + WAF + Shield Std you configure
  • Network: VPC, SGs, NACLs, private subnets strongest isolation
  • App: ALB mTLS, IAM auth, Cognito deep
  • Data: KMS/BYOK, RDS encryption full control
  • You own: config correctness, patching, least-privilege IAM large surface

Vercel + Railway + CF

  • Edge: CF WAF + DDoS + Bot Mgmt best-in-class, included
  • Network: managed, mostly public + tokens limited isolation
  • App: Worker pre-auth (JWT/Access) edge auth
  • Data: provider-managed encryption less control / no BYOK on Railway
  • You own: origin-lock secret, env-var hygiene small surface

GCP

  • Edge: Global LB + Cloud Armor strong
  • Network: VPC, Cloud Run ingress=internal, connectors strong isolation
  • App: IAP, Cloud Run IAM + ID tokens deep
  • Data: CMEK/BYOK, default encryption full control
  • You own: IAM, Armor policies medium surface

Azure

  • Edge: Front Door WAF + DDoS Standard bundled strong at-edge control
  • Network: VNet, NSGs, Private Link, Container Apps VNet integration full isolation
  • App: Managed Identity, Entra ID Conditional Access AD-native auth
  • Data: Key Vault BYOK, default encryption full control
  • You own: Azure portal complexity, IAM role design steeper learning curve

Quick read

Cloudflare owns the edge layer better than anyone — biggest single security win for a public single-domain app. AWS/GCP/Azure own network + data control. Azure is uniquely strong for Microsoft-ecosystem/AD-integrated workloads. The PaaS stack trades deep network isolation for a much smaller surface you can actually get right.

6 Which should you pick?

Pick the PaaS stack if…

✓ Cost at low/medium traffic is the priority

✓ Small team, no dedicated DevOps

✓ Want to ship in days, iterate fast

✓ Most of 300 projects are low-traffic / idle

✓ Standard SaaS compliance is enough

✗ Avoid if: heavy sustained load, deep network isolation, or strict single-vendor procurement

Pick GCP if…

✓ You want serverless economics but on one hyperscaler

✓ Scale-to-zero + fast cold starts matter

✓ Need enterprise compliance (HIPAA/PCI/FedRAMP)

✓ Want portable Knative containers (low lock-in)

✓ One bill, one IAM, one support contract

~ Watch: egress + Global LB base pricier than Cloudflare

Pick AWS if…

✓ Heavy, sustained, predictable traffic

✓ Deep VPC isolation / private networking required

✓ Strictest regulated workloads

✓ You have a platform team + use Savings Plans/Spot/Graviton

✓ Already all-in on AWS ecosystem

✗ Avoid if: 300 idle services & small team — fixed infra tax kills you

★ Pick Variant ④ (GCP+CF) if…

✓ You want the lowest serverless-on-hyperscaler bill (no LB floor)

✓ Want free best-in-class WAF/DDoS at the edge for all 300 apps

✓ Need Cloud Run compliance + network isolation on the backend

✓ One JS routing layer for host/path across the fleet

✓ OK running two vendors (GCP + CF) but only the Worker to operate

~ Must lock origins (secret header + internal ingress) so CF can't be bypassed

Pick Azure if…

✓ Already in Microsoft ecosystem (Office 365, Teams, AD)

✓ Need hybrid / on-prem integration (Azure Arc)

✓ AD auth built-in is a hard requirement

✓ Broadest compliance cert portfolio (HIPAA/SOC2/ISO/FedRAMP)

✓ Enterprise SLAs with TAM support preferred

✗ Avoid if: cost-sensitive — Front Door $35 base is expensive; complexity exceeds GCP for pure serverless

Hybrid (often best)

Cloudflare as the universal front door (DNS + WAF + DDoS) for any backend.

Vercel for the 100 frontends (best frontend DX/edge).

Cloud Run or Railway for the 200 backends depending on compliance needs.

Keep AWS only for the few heavy/regulated services. Route everything through the one Worker domain.

7 Operational & security add-on costs

Costs that are required to face a client — logging, monitoring/observability, security add-ons, backup/DR, and support. These sit on top of the compute totals in Section 2 and are frequently under-estimated. All figures are estimates at medium-traffic tier (1K req/day/project) unless noted.

Why this matters: A production deployment without structured logging, alerting, WAF managed rules, and a support contract is not client-ready. These add-ons commonly add $150–$800/mo to the baseline compute bill and shift the cost ranking between strategies significantly.
